# Car Rental & Fleet Booking System REST API

A production-quality REST API backend for a **Car Rental & Fleet Booking System** built with **Node.js**, **Express.js**, and **Supabase (PostgreSQL + Auth)**.

---

## 🛠 Tech Stack

- **Runtime**: Node.js (v18+)
- **Framework**: Express.js
- **Database & Auth**: Supabase (PostgreSQL with Stored Procedures & Supabase Auth)
- **Client Library**: `@supabase/supabase-js`
- **Environment Management**: `dotenv`
- **CORS**: `cors`
- **Development Tooling**: `nodemon`

## 🗄 Database Schema (DDL)

Run the following SQL in your **Supabase Dashboard -> SQL Editor**:

```sql
-- 1. Vehicles Table
CREATE TABLE IF NOT EXISTS vehicles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    brand TEXT NOT NULL,
    model TEXT NOT NULL,
    year INT NOT NULL,
    category TEXT NOT NULL CHECK (category IN ('Sedan', 'SUV', 'Luxury', 'Hatchback', 'Electric')),
    daily_rate NUMERIC(10, 2) NOT NULL CHECK (daily_rate > 0),
    fuel_type TEXT NOT NULL,
    seating_capacity INT NOT NULL DEFAULT 5,
    status TEXT NOT NULL DEFAULT 'available' CHECK (status IN ('available', 'rented', 'maintenance')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 2. Rentals / Bookings Table
CREATE TABLE IF NOT EXISTS rentals (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id UUID NOT NULL,
    vehicle_id BIGINT REFERENCES vehicles(id) ON DELETE RESTRICT,
    customer_name TEXT NOT NULL,
    customer_email TEXT NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    total_cost NUMERIC(10, 2) NOT NULL,
    status TEXT NOT NULL DEFAULT 'booked' CHECK (status IN ('booked', 'active', 'completed', 'cancelled')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    CONSTRAINT valid_date_range CHECK (end_date >= start_date)
);

-- 3. Collision Check Index
CREATE INDEX IF NOT EXISTS idx_rentals_vehicle_dates ON rentals (vehicle_id, start_date, end_date) 
    WHERE status IN ('booked', 'active');

-- 4. Reusable SQL Function for Availability / Collision Check
CREATE OR REPLACE FUNCTION check_vehicle_availability(
    p_vehicle_id BIGINT, 
    p_start_date DATE, 
    p_end_date DATE, 
    p_exclude_rental_id BIGINT DEFAULT NULL
) RETURNS BOOLEAN AS $$
DECLARE
    conflict_count INT;
BEGIN
    SELECT COUNT(*) INTO conflict_count
    FROM rentals
    WHERE vehicle_id = p_vehicle_id
      AND status IN ('booked', 'active')
      AND (p_exclude_rental_id IS NULL OR id != p_exclude_rental_id)
      AND start_date <= p_end_date
      AND end_date >= p_start_date;
    RETURN conflict_count = 0;
END;
$$ LANGUAGE plpgsql;
```

## 🔑 Supabase Keys & Security Strategy

- **`SUPABASE_SERVICE_ROLE_KEY` (Recommended for Backend)**:
  This backend uses the Service Role key for database queries when available. Since Row-Level Security (RLS) policies are not specified in the initial DDL, using the Service Role key allows the trusted backend server to safely perform inserts, joins, and cascading updates without being blocked by default-deny RLS settings.
- **`SUPABASE_ANON_KEY`**:
  Supported as a fallback when RLS is disabled in Supabase.
- **Supabase Auth (`auth.getUser`)**:
  Regardless of the database client key used, every protected request validates the incoming Bearer JWT against `supabase.auth.getUser(token)` and checks `req.user.id` to ensure strict tenant isolation.

## 📅 Collision Detection & Pricing Engine

### Collision Detection Algorithm
A vehicle cannot be booked if any existing booking for that vehicle has status in `('booked', 'active')` and overlaps with the requested interval `[start_date, end_date]`.

Two intervals `[A_start, A_end]` and `[B_start, B_end]` overlap if and only if:
$$\text{Existing.start\_date} \le \text{Requested.end\_date} \quad \text{AND} \quad \text{Existing.end\_date} \ge \text{Requested.start\_date}$$

- The system calls the PostgreSQL stored function `check_vehicle_availability(p_vehicle_id, p_start_date, p_end_date)` via `supabase.rpc()`.
- If the RPC is unavailable, the application gracefully executes an equivalent indexed fallback query directly on the `rentals` table.

### Server-Side Pricing
- **Formula**: $\text{total\_cost} = \text{rental\_days} \times \text{daily\_rate}$
- **Minimum Rental Duration**: Minimum 1 day is charged for same-day bookings (`start_date == end_date`).
- Calculated strictly on the server to prevent client-side tampering.

## 📋 Architectural Decisions & Assumptions

1. **Supabase Key Selection (`SUPABASE_SERVICE_ROLE_KEY` vs `SUPABASE_ANON_KEY`)**:
   - The server defaults to `SUPABASE_SERVICE_ROLE_KEY` (with graceful fallback to `SUPABASE_ANON_KEY`).
   - Rationale: The database schema relies on standard PostgreSQL foreign keys, check constraints, and indexes without requiring custom PostgreSQL Row-Level Security policies. Operating with the service role key on the Node.js backend allows standard administrative updates (like vehicle status updates and join queries) while keeping API-level security strictly validated in Express middleware.
2. **Vehicle Status Lifecycle**:
   - When a booking is created where `start_date <= today`, the vehicle's `status` is automatically updated to `'rented'`.
   - For future-dated bookings (`start_date > today`), the vehicle's current status remains `'available'` so it can still be booked for other non-overlapping time slots.
   - When a booking is cancelled or marked completed, the vehicle status is restored to `'available'`.
3. **Ownership and Privacy on Cancel / Complete**:
   - `PATCH /api/rentals/:id/cancel` and `PATCH /api/rentals/:id/complete` enforce owner matching (`user_id = req.user.id`).
   - If a user tries to access a rental ID that belongs to someone else, the API returns `404 Not Found` rather than `403 Forbidden` to prevent leaking rental ID existence across tenants.
4. **Cancellation Rules**:
   - Cancellations are permitted only before the rental's `start_date` has arrived.
   - Once a reservation date is active or past, cancellation is rejected with `400 Bad Request`.
5. **Same-Day Rental Pricing**:
   - If `start_date == end_date`, the system computes a minimum duration of 1 day to ensure appropriate billing.
6. **Hard Deletion vs Historical Integrity (`ON DELETE RESTRICT`)**:
   - Active bookings block vehicle deletion at the application layer.
   - The PostgreSQL foreign key `REFERENCES vehicles(id) ON DELETE RESTRICT` protects historical data integrity if completed or cancelled bookings exist. The API catches this error code (`23503`) and presents a friendly message suggesting the vehicle status be changed to `maintenance` instead.
